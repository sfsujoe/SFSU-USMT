# SFSU USMT project runbook

Last updated: 2026-11-07 (America/Los_Angeles)

## Project purpose

Improve the technician workflow for backing up and restoring employee files and settings before computer re-imaging or replacement. The existing toolchain wraps Windows User State Migration Tool (USMT). The intended experience has one clear entry point that guides the technician through Backup or Restore.

This is the maintained project record, not an approved procedure for performing a production migration. Keep current state and next steps near the top; preserve concise decision and session history below.

## Current state and handoff

- Phase: local discovery/preparation app plus an agreed migration design. App/Scripts handles identity/profile inventory, metadata-only backup preparation, offline restore review, shared appearance and reporting. ScanState/LoadState remain disconnected; no new-engine migration, browser coverage or EFS decryption test has run.
- Main-app launch presentation (2026-11-06, D63): a normal no-argument CMD launch starts a hidden PowerShell host and the existing graphical masked account/password dialog. A brief CMD flash may occur; the launcher returns after starting the process. Argument-based commands remain visible/synchronous. Entry-script GUI startup failures display a saved log path or an unsaved-log explanation; use sfsu-usmt.cmd -LdapServer ad.sfsu.edu for visible startup/policy troubleshooting. Credential collection/authentication, caller privileges, process-only Bypass and all D62 rules are unchanged.
- Identity generalization implemented 2026-11-06 and published 2026-11-07 (D62/D64): IDs are bounded text, independent of SAM account name, UPN and profile folder spelling; exact matching SID anchors AD verification and name refresh. Shared Sfsu.Identity.psd1 configures the ID attribute (default sAMAccountName) and login suffixes (default sfsu.edu). Alphabetic/longer/p-prefixed logins are allowed. Manual domain identity requires an explicitly confirmed ID and name. Schema-three preparation metadata replaces earlier development versions, which remain visible as unrecognized without conversion/deletion. No legacy-store importer was implemented. See [identity guide](docs/IDENTITY.md).
- Migration design (2026-11-04, D46-D60): prefer native USMT and small XML policy changes. Retain useful outside-profile/shared/legacy documents. Exclude all Defender migration data, cloud roots/caches (including custom locations), EXE/MSI, browser caches, Windows temporary data and TMP. Use default USMT Office rules except exclude OST. Capture Edge/Chrome/Firefox history and bookmarks. Assume cloud uploads have completed; no automatic sync-status audit/gate is selected. Cloud-location discovery/reporting and manual unresolved-root review are approved designs, not implemented functionality.
- EFS and storage: use /efs:copyraw and preserve user certificate/private-key/DPAPI components; test that the intended user can decrypt restored files. Backup stores are unencrypted; EFS keys are separate from store-encryption keys. Use the established portable launcher/App/Backups/Logs layout and preserve existing backups/settings. Retention and printers remain deferred; no automatic backup deletion is authorized.
- Restore: only the original domain identity or a newly recreated local account. No different-domain-account mapping, local-to-domain conversion, reuse of existing local accounts, or general merge workflow. Preflight all selected targets before any LoadState/account/data changes; an existing target local account or destination employee profile/folder stops the whole restore and notifies the tech. Domain identity already existing in AD is expected; treating destination profile/folder presence as the domain collision condition is the assistant's stated operational interpretation. Local password/enablement/group-membership details remain unspecified; do not infer enabled blank-password accounts or admin changes.
- Operation/platform: hands-off after initial choices, with native bounded error handling/retries, automatic verification and truthful final reports; no per-file babysitting. Desired matrix is Windows 10+ capture, Windows 11-only restore, applicable x64/ARM64. Windows 7 was corrected by the user and is no longer in scope. Exact error-control rules, native process cancellation, prerequisites and all architecture transitions still need implementation/tests.
- Fresh evidence: the App payload has amd64/arm64/x86 ScanState/LoadState/UsmtUtils reporting 10.0.26100.9457; archived tools previously reviewed report 10.0.26100.1. The current App's old Firefox/Chrome rules and lack of an explicit modern Edge component do not fulfill the browser requirement by themselves. No executable was launched during payload inspection. Vendor binaries remain local/Git-ignored and are absent in a fresh clone.
- Supplied legacy field logs: the ignored archive/legacy-and-mockup/log examples folder contains a November 2 scan ending Success/no migration errors recorded, a November 4 load ending Success with 144 /c-bypassed errors, and populated MigLog.xml. All 144 failed XML operations belong to Defender (112 file, 32 registry); additional text diagnostics include Office hierarchy and Offline Files/plugin errors. Successful operations demonstrate outside-profile collection and native Downloads handling. User certificate/crypto/DPAPI operations succeeded, but no particular EFS key/file match or decryption was checked. These are inspected user-produced legacy results, not proof of new-app capture/restore or exhaustive coverage. Details: [workflow review](docs/CURRENT-WORKFLOW-REVIEW.md).
- Authentication retains D43's explicit Kerberos-only signed/sealed LDAP on 389, timeout/retry/expiry and no implicit Windows/NTLM fallback. D62 supersedes the standard-only/p-account prohibition. The standalone diagnostic now shares the application's generalized login policy; its transport and exact-account/SID scope are unchanged. D45 still defers LDAPS/CBT investigation. Earlier user reports support two LDAP transports on one domain-joined host/DC, not CBT enforcement or acceptance of the generalized app across the full host/profile/share matrix.
- Publication completed (2026-11-07, D64): the reviewed 20-file identity/launch/source/test/documentation set was committed as 41a0c5f (Generalize SFSU identities and streamline graphical launch) and pushed from 39b497a to main at https://github.com/sfsujoe/SFSU-USMT.git. GitHub advertised 41a0c5fd70a55acaa0a6152a50a409f7e4e7f09a, exactly matching local HEAD after that source push; the working tree was clean. This verified outcome is captured in a subsequent documentation-only commit. Generated logs/reports, employee data, archive, vendor payload, Backups and runtime Settings remain excluded. No share deployment or migration occurred.

### Deferred printer migration add-on (D40)

- User-confirmed planning assumptions: university printers use direct TCP/IP or IPP and are onsite. Employees may install personal printers at home, with no university control over device type or installation method. Printer ownership cannot be inferred from protocol, private IP address or current reachability. No actual printers were inventoried in this chat.
- Microsoft documents USMT support for network printer mappings during online migration, with no printer-driver/local-printer migration and no network-printer mapping in offline migration. The archived x64 Config.xml printer-related migrate=no entries were checked and are inside a comment; they are not active exclusions. This is static evidence, not proof of printer coverage in the original scripts or supplied USMT version.
- Proposed future add-on: capture machine-wide queue/port/driver data separately from selected-user connections/defaults into each backup's metadata; preserve complete IPP URLs and TCP/IP port details. Offer technician review, duplicate detection and per-printer outcomes. Restore supported TCP/IP/IPP configurations with compatible installed/approved drivers and platform-capability checks; record unknown USB/WSD/vendor-specific installations for manual review rather than promise universal restoration. Consider personal devices unavailable onsite deferred/unverified without failing the employee backup solely for lack of printer reachability. These actions are recommendations, not agreed implementation details.
- Open design questions: ownership confirmation or a university device inventory; selected-user discovery/restoration while the desktop is local admin; default-printer behavior; signed-driver and architecture/version compatibility; IPP cmdlet availability and URL/certificate/authentication handling; vendor apps/preferences; and repeatability without overwriting existing destination queues.
