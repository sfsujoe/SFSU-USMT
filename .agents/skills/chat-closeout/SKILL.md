# Chat closeout

Update [PROJECT-RUNBOOK.md](../../../PROJECT-RUNBOOK.md) so another project chat can resume without this conversation. Resolve the link relative to this skill's installed directory, not the shell's working directory. The project root is three directories above `.agents/skills/chat-closeout/`.

1. Read the root [AGENTS.md](../../../AGENTS.md) and the complete current runbook. Review the available conversation, changed files, and recorded validation results. Use Git status/diffs when Git metadata exists; otherwise inspect relevant files directly. Do not initialize Git or execute migration scripts to produce evidence.
2. Reconcile the current-state summary, confirmed decisions, milestones, backlog, validation limits, open questions, and next actions. Keep the summary useful for the next chat, not merely an append-only transcript. Capture specific file paths and operational constraints when they affect continuation.
3. Record user decisions as decisions and assistant recommendations as proposals. A topic discussed without an implementation request stays proposed. Mark work complete only when evidence supports it; distinguish implementation, user acceptance, static checks, UI checks, and actual migration tests. Preserve superseded decisions with a brief explanation instead of erasing their history.
4. Update the last-updated date and add a concise session-history entry using America/Los_Angeles dates. Include material changes, validation performed or not performed, unresolved issues, and a concrete next action. Identify claims based on user reports. If an entry already covers the same work, update it or leave it alone; repeated invocation without new information should not create duplicate entries or refresh the date needlessly.
5. Before saving, check the current on-disk record for intervening edits and merge rather than overwrite unrelated updates. Re-read the saved runbook and check that changed paths exist, the milestone state matches the summary, and proposals have not become approvals. If no substantive information changed, report that it is already current.
6. Prepare the GitHub handoff after updating the runbook. The user-designated repository is `https://github.com/sfsujoe/SFSU-USMT.git`; a later explicit user instruction can change it. Review the intended file set and available validation, and summarize the project changes, repository, and target branch when known. Keep migration stores, employee data, credentials, encryption keys, and generated migration logs out of the publishing set. Do not stage unrelated user changes.
7. Ask whether to commit and push the reviewed project changes to that repository. Use an available user-input tool when continuing the closeout; otherwise put the question in the final handoff. The question must follow a concrete change summary, not precede the runbook work. If the local folder has no Git metadata, explain that connecting it to the repository while preserving remote history is required, and include that setup in the question. Determine the branch from existing tracking information or the remote default before publishing; do not invent a branch name or assume the repository is empty. If there are no changes or unpushed commits, report that nothing needs pushing instead of asking to publish an empty change.
8. Wait for the user's answer before Git setup that changes the checkout, committing, or pushing. A clear yes to the concrete commit/push proposal authorizes the necessary agreed Git preparation and normal push. If they decline or defer, leave changes local. A missing answer is not approval. Do not force-push or overwrite remote history; handle missing access or an unresolved target as a specific blocker rather than retrying publication blindly.
9. Record the user's choice and any actual commit/branch/push result in the runbook. State clearly if a handoff note remains local after a push; never claim uncommitted notes are published. Return a short closeout with the runbook link, material updates, validation gaps, next action, and publishing outcome or pending question. A request only to edit this workflow is not itself a closeout request.

Invocation by itself authorizes updating this project record and preparing the publishing question. It does not authorize implementing the backlog, running USMT, changing employee accounts or permissions, moving/deleting backups, deploying to the share, committing/pushing, changing saved execution policies, messaging others, or closing/archiving the chat. The user's answer to the concrete publishing proposal can separately authorize the agreed Git setup, commit, and push.

Keep credentials, encryption keys, employee contents, and unneeded personal identifiers out of the runbook. Record only facts supported by accessible evidence; when earlier chat context is missing, retain uncertainty rather than reconstructing decisions from guesses. If the linked runbook cannot be found, use a project path explicitly provided by the user or explain the missing record instead of writing to a guessed location.
