# SFSU User State Migration Tool

Project planning and development for a guided employee backup and restore toolkit using Windows User State Migration Tool (USMT).

The portable application now connects native USMT capture and restore for controlled validation. Domain IDs come from a configured AD attribute through exact-SID lookup, or explicit manual confirmation. IDs, Windows account names, UPNs and profile paths are separate. Local accounts retain their username/SID and require an assigned display name. Synthetic tests do not establish real migration, account provisioning, EFS decryption or platform/share acceptance. Read the [migration guide](docs/MIGRATION.md) before VM testing.

Open `sfsu-usmt.cmd`. The startup dialog accepts an **SFSU account login or full UPN and password**, or **Continue without AD** for manual identity confirmation. Letters, longer IDs and p-prefixed credentials are supported. Bare logins use the configured suffix (currently `@sfsu.edu`). Explicit Kerberos-only signed/sealed LDAP refuses NTLM/default-credential fallback. Credentials expire after ten minutes without directory activity. Every selected profile requires a name. **Back up selected profiles** reviews cloud/custom-browser locations, estimates size, captures each signed-out profile to a compressed unencrypted store with `/efs:copyraw`, and runs native store verification. Useful outside-profile document discovery is retained; cloud/Defender/EXE/MSI/OST/browser caches/Windows temp/TMP are excluded, with Edge/Chrome/Firefox bookmarks/history explicitly included. Cloud uploads are assumed complete.

**Restore selected backups** preflights every target and verifies every source store before account/data changes. Existing target local accounts or employee profile/folder collisions stop the whole batch. Domain identity remains the original SID. Each recreated local account gets its own masked password/confirmation, required enabled-state choice and Administrators choice defaulting to No. Accounts start disabled and receive verified final choices after apply. Passwords are session-only and never enter metadata, reports or process arguments. Failed/cancelled runs preserve partial data and disable only accounts created by that run. Native logs, tool/policy hashes and truthful acceptance warnings are retained; intended-user EFS decryption/application fidelity still require actual restore testing. Cancel terminates the native job and descendants without rollback/deletion. App, Backups and Logs follow the package location; existing backups are preserved.

A normal launch requests Windows administrator approval before opening the graphical app/sign-in dialog, unless already elevated. The PowerShell console stays hidden; the CMD may appear briefly and returns after starting the app. Cancellation stops startup with a graphical explanation. A mapped entry path is resolved to UNC before elevation; the elevated account must still have package/share access. No drives are remapped or credentials transferred. Startup errors show a saved log path or explain that a log could not be saved. Headless/developer/maintenance actions retain the caller's privileges and synchronous output/exit codes. GUI launches with arguments (for example `-LdapServer ad.sfsu.edu`) also request elevation; if relaunched, they wait for the elevated app and return its result. For visible startup/policy diagnostics, run the entry script from an already elevated PowerShell console. Kerberos, separate AD credentials and process-only execution policy remain unchanged.

Account renames and unrelated or suffixed profile-folder names are supported through the matching SID. SID/multiple-match conflicts remain blocked. See [Identity configuration](docs/IDENTITY.md) for the shared attribute/suffix policy, manual identity entry and schema-three metadata. Earlier development metadata versions are intentionally unsupported and remain visible as unrecognized. Exclusion counts explain unsupported/system/setup/missing/linked profiles. Runtime path guards reject filesystem links and protect directories during writes. See [Security and maintenance](docs/SECURITY.md) for permissions, bounded reporting, explicit log-retention commands, acceptance checks, and future engine requirements. User-editable scripts are an accepted risk; the application does not provide a security boundary against an administrator or a compromised endpoint.

The main window starts maximized and is titled **SFSU User State Migration Tool**. Its **By Academic Technology at SF State** attribution links to [Academic Technology](https://at.sfsu.edu/). The startup AD dialog stays normal-sized and centered, emphasizes its sign-in instruction, explains that AD resolves SFSU ID to Display Name, and prefixes authentication failure messages with ⛔. Profile discovery excludes the Windows setup account `defaultuser0` by exact account or profile-folder name, ignoring case; its files and account are not modified.

**Theme & Font**, at the bottom right (Alt+T), previews SFSU Classic, Ocean, Forest, Warm, Dark Mode, or Windows system colors and offers 100–200% text sizes. **Use theme** saves the shared preference inside `App/Settings/appearance.json`; all technicians using that toolkit load it on their next launch. No per-computer or per-user preference file is written. Windows high contrast overrides custom colors automatically without changing the saved choice. Cancel/Escape restores the previous appearance. The main screen has no theme-name label. Keyboard access, readable verification text, accessible names/status notifications, wrapping actions, and resizable dialogs support accessibility; full assistive-technology/Windows contrast/DPI acceptance testing remains necessary before claiming compliance.

Printer migration is deferred as a future optional add-on. University printers are assumed to use onsite direct TCP/IP or IPP; personal printers can use uncontrolled installation methods. No printer inventory or restoration is implemented. The proposed scope and unresolved compatibility/user-context questions are recorded in the runbook.

## Chat workflow

Use `$start-chat` to load project context and `$chat-closeout` to update the runbook. Both project-local skills live in `.agents/skills/`. Closeout includes a question about committing and pushing project changes; publishing requires the user's answer.

## Local reference archive

Legacy scripts, the UI mock-up and logo, and the supplied USMT toolsets are retained locally in `archive/legacy-and-mockup/`. That folder is ignored by Git and is not included in a clone of this repository. Links into it in the project records require the local reference copies.

The archived scripts operate on employee data and are reference material. They are not the new production toolkit.

The supplied logo under `App/Assets/` is included with the application source. User-supplied ADK files under `App/User State Migration Tool/amd64` and `arm64` are Git-ignored and must be supplied separately with their DLLs, XML and manifests. The GUI/report preview can open without them; migration checks required files, native architecture, matching builds and Microsoft signatures and refuses invalid/missing dependencies. Keep the complete App/Scripts set, including the new engine C# source and policy/UI modules, beside the launcher. Runtime Backups, Logs, App/Settings and tests/.work remain ignored and must be preserved during updates. Developer-only synthetic reports remain available with `sfsu-usmt.cmd -Headless -Scenario Failed`.
